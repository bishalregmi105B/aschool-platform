## 2. V1 RESIDUE (shipped but not yet promoted; ratchet armed but never fired)
- The ratchet IS enforced structurally — `_ratchet()` flips 7 checks to error when `schema_version: 2` (`validator.py:229-231`, used at `:244,381-397,521-526,558-565`) — but is **inert**: zero manifests at v2, `--fix-safe` evidently never run. The warnings→errors ratchet exists in code, not in practice.
- All 41 manifests are adapter-dependent; loader still mirrors v1 pointers back out for legacy readers (`loader.py:73-76`), and `refresh_registry` reads v1 top-level keys (`loader.py:483-497`).
- `SIDEBAR_SUPERSEDED_BY` and `SLUG_SECTION_MAP` remain hardcoded fallbacks (`loader.py:563-635`) — correct per spec (manifest `section:`/`supersedes:` are v2 upgrades), but no manifest supplies them yet.

- Legacy flat manifests dir `backend/app/plugins/manifests/*.yaml` (8 files) still live (wave 6 of PTTA §1.4c not started).

Any plugin bumping config_version past 1 today would silently skip migration on read.

## 4. EVENTS.YAML vs LISTENERS.PY
`events.yaml` (emits/consumes contract file, D2 §A.1) is **not implemented and not shipped by any plugin**. What exists instead: (a) inline `events: emits/listens` string lists in 27 manifests — unread by any code; (b) the runtime bus `events.py` + `listeners.py` (19 handlers, wired at `app/__init__.py:587-588`); (c) 10 call sites of `emit_for_school`/`emit_async` across `app/api/v1` and `app/tasks`. The loader has **no `load_listeners()`** (grep: 0 hits) — listeners.py is a single global module, not per-plugin autoload; a plugin cannot ship `listeners.py` and get it imported. So the emit side is real, the declared contract side is vapor, and third-party event consumption is impossible by construction.

## 5. WIDGET CUSTOMIZATION GAPS (what blocks a school editing a widget)
Backend `widgets.py`/`widgets.yaml` already model per-school config (`config_schema` field in the widget record, `widgets.py:137`) and PTTA §2.3 says school widget config merges from `SchoolPlugin.config["widgets"][<key>]` — but `GET /plugins/widgets` **never merges it** (`plugins.py:1048-1053` passes no config; `widgets_for` has no config param, `widgets.py:154-207`). Concretely missing:
1. **Per-widget config**: no `config_schema:` on any of the 23 shipped widgets (grep: 0); no PUT surface for `SchoolPlugin.config.widgets.<key>`; `PluginWidgetHost` accepts a `config` prop (`registry.ts:24-26`) but `WidgetSlot` never supplies one (`PluginWidgetHost.tsx:225-231`).
2. **Per-slot layout persistence**: `dashboard_layouts` table (PTTA §2.7) does not exist — no `dashboards` API module (`ls backend/app/api/v1 | grep dash` → nothing), no dnd-kit edit mode; `default_layout` is computed fresh from `default: true` declarations every request (`widgets.py:210-217`, `plugins.py:1060`). A school cannot reorder/add/remove widgets; it sees exactly what YAML authors defaulted.
3. **Per-role visibility UI**: role gating is server-side only (`widgets.py:182-183`); no UI for a school to override visibility per role; validator roles are fixed (`validator.py:102-111`).
4. **Widget settings popover / FormRenderer at widget level** (PTTA §2.7 third entry point): absent — WidgetFrame/overflow-menu from D2 §B.4 was never built (no configure/hide affordance; host renders bare cards, `PluginWidgetHost.tsx:161-165`).
5. `params_from` slot bindings are normalized (`widgets.py:108`) but no frontend consumer resolves them for context-propagation into dependent widgets (only `useWidgetData(..., extraParams)` exists).
Alignment with the D2/PTTA contract is otherwise good: slots are the closed host set (`validator.py:77-98` matches PTTA §2.2), `$`-binding tokens resolve client-side (`bindings.ts`), component tokens are compile-time-only (`registry.ts:1-15`), public_site surfaces require `capabilities.public_routes` (`validator.py:490-497`).

## 6. THEME + PARITY STATUS
- Theme engine is **v1 only**: duplicated registries — `backend/app/services/website/theme_engine.py:35-106` (`THEMES` dict, 10 themes, 5 colors + 2 fonts) and `frontend/themes/registry.ts` (159 ln) — plus `synced_colors`/`apply_theme` write path (`theme_engine.py:185-245`) and a thin `GET /themes` API (`api/v1/themes.py:14-22`). There is **no** `backend/app/themes/` dir, no `base.yaml`, no `theme_documents`/`school_theme_tokens` tables, no `services/theme/resolver.py`, no `GET /themes/tokens` (grep: none).
- **Parity lock: NOT BUILT — and nothing has touched themes, so nothing has broken it.** `backend/scripts/capture_theme_baseline.py`, `tests/test_theme_baseline.py`, `frontend/__tests__/theme-parity.test.ts`, and the Playwright zero-threshold visual diff (D2 §D.4 items 1-3) are all absent. `UNIFIED_ROADMAP_2026-09.md:247` mandates "parity lock before any theme work"; the honest status is *neither exists yet*, so the ordering rule is still satisfiable — but the moment anyone edits a theme (or a plugin ships `theme_contributions`), they do so with no safety net. Today's protections are only the pre-existing color allowlists (`theme_engine.py:17-25`, `white_label.py:32`) and client sanitizer.
- School sites render **theme-driven already, not hardcoded**: `app/school/[slug]/layout.tsx` picks `themeCss + surfaceOverride + customCss + 2 resets` into one `<style>` (`layout.tsx:229-239`), sets `data-theme`, canonical+OG (`:52-63`), JSON-LD script (`:187`). But the palette source remains the duplicated pair above (7 declarations via `generateThemeCSS`), not a resolved token document. Dashboard/Flutter/PDF consume no theme tokens (D2 §D.2 consumers 2-4 unstarted).

- **W-02 draft/live: partial, backend-only.** `SchoolWebsite.draft_config`/`is_published`/`published_at` exist (`models/school.py:203-205`) and `WebsitePage.is_published` gates SSR (`website.py:240-241`, S-12 draft block `:324-328`). But there is no undo, no version history, no draft-preview route, no draft/publish UI flow beyond a boolean.
- **W-03 SEO ✅ largely done**: per-school sitemap at request time (`app/school/[slug]/sitemap.ts:1-20`), robots.ts, canonical + alternates (`layout.tsx:57-58`), JSON-LD (`layout.tsx:187`), meta/OG on pages (`models/website.py:22-26`). Remaining: hreflang/i18n alternates.
- **W-04 contact inbox ✅ core done**: `POST /website/public/<slug>/contact` persists to `ContactMessage` + audit trail (`website.py:490-507`), rate-limited (`:472`); admin inbox `GET /contact-messages` unread-first (`website.py:851-890`). **But there is no dashboard UI consuming it** (grep of `frontend/app/dashboard` for contact inbox: none) and school-profile extended fields (part of W-04) are absent — `SchoolWebsite` carries only theme/SEO/pixel columns (`models/school.py:195-210`), no address/hours/staff-profile fields.

## 8. TEMPLATE PACKS: what exists vs orphan scripts
Six template systems, none unified (PTTA §5.1): designer folder packs (`backend/app/templates/designer/` — 40 folders) merged with in-code `TEMPLATES` (`services/designer/template_engine.py:898+`), website sections in `frontend/lib/school-website/registry.ts`, 3 page presets in `lib/school-website/templates.ts` (applied from the themes tab, `app/dashboard/website-builder/themes/page.tsx:8,238-241`), themes (§6), notification strings inlined in `listeners.py` (~15 f-strings), and generator scripts.
- **No `TemplateRegistry`, no `pack.yaml` anywhere, no `template_packs` table, no `/templates/packs` API, no `kind: website_section` packs** — PTTA §5.2-5.3 is unimplemented. `/website/section-types` does not exist; the section registry is frontend-only static data.
- `tools_gen_*.py` at repo root (calendar `tools_gen_calendar_templates.py:9-13`, nepal writer+designer `tools_gen_nepal_school_templates.py:3-24`, redesign, thumbnails) write `template.yaml`+`canvas.json`/`writer.json` straight into `backend/app/templates/designer/<key>/` and are **orphan-ish**: consumed only by the designer folder scanner (`services/designer/template_folders.py`), not by any template-pack architecture. PTTA §5.7 explicitly plans to keep them working and later emit `pack.yaml` — that later step has not happened.
- Plugins cannot feed pre-built pages/blocks to a school site today: `template_packs[]`/`theme_contributions[]` manifest keys are validated-if-declared (`validator.py:340-353`) but nothing scans them; a plugin's only website lever is manually editing `WebsitePage.sections` rows.

## 9. TEMPLATE-PACK ARCHITECTURE GAP — minimal spec to close (spec only, design-preserving)
Goal (PTTA §5.5b): `nepal_curriculum` ships an "Academics" page template using its widgets; any installed plugin contributes website sections/page presets without touching rendered design. Minimal architecture, in dependency order:
1. **`TemplateRegistry` scanner** (`backend/app/services/templates/registry.py`): scan `backend/app/templates/<kind>/<pack_key>/pack.yaml` + `modules/<slug>/templates/<pack_key>/pack.yaml` for installed plugins; `resolve(kind, pack_key, school_id)` = school override (DB row) → plugin → platform → legacy in-code. Kinds needed now: `website_section`, `website_page_preset`, `document` (designer compat), `notification` (later).
2. **17 section packs** copied *verbatim* from `frontend/lib/school-website/registry.ts` `defaultContent`+`controls` into `backend/app/templates/website_section/<type>/pack.yaml` (17 types enumerated at `SectionRenderer.tsx:976-1008`); serve `GET /website/section-types`; switch `SectionRenderer` from `case` ladder to a `SECTION_COMPONENTS` map; keep unknown-type placeholder (`SectionRenderer.tsx:1013-1018`) as the plugin-extension point.
3. **Plugin widget of `type: website-section`** (validator already whitelists it, `validator.py:74`; slot `website.section` already legal, `validator.py:94`): plugin pack carries `renderer_token` = an existing section type (spec renderer) or a new compile-time token; data via a `public: true` GET on the plugin's own blueprint; `/website/public/<slug>` gains a `plugin_sections` block (single fetch preserved, `website.py:254+`).
4. **Page presets as packs**: convert `lib/school-website/templates.ts` presets to `kind: website_page_preset` packs; apply flow unchanged (writes sections exactly as `themes/page.tsx:238-241` does today).
5. **Guardrails**: `capabilities.public_routes: true` prerequisite (validator rule already coded, `validator.py:490-497`); `defaultContent`/`controls` byte-equality snapshot test so pack conversion provably changes no pixels; plugin packs may not override a core section type's renderer, only add keys. Design system untouched — the rendered site consumes the same `SectionRenderer` components.
6. **Later (same registry)**: notification packs replacing `listeners.py` inline strings (PTTA §5.6, SMS segment warnings); designer `template.yaml` compat normalization so `tools_gen_*` output joins the catalog unchanged (§5.7).

## 10. MOBILE MANIFEST MAPPING
- Manifests carry v1 `flutter: {<role>_app: {feature_folder, tabs}}` (e.g. `modules/exams/manifest.yaml:42-48`, 41/41 manifests); the adapter normalizes to `mobile.<role>` (`loader.py:100-107`) — but **nothing consumes it**. `GET /mobile/bootstrap` (`api/v1/mobile.py`) builds visibility from `_visibility_for_role`'s hardcoded per-role rule lists (`mobile.py:159-230+: _build_visibility` tuples), not from manifests; no `mobile.yaml` exists; aschool_shared has no widget/plugin-spec consumption (grep: 0 hits). The flutter keys are documentation.
- What a real "plugin ships a mobile screen" path needs (PTTA §2.6, D2 §B.5): (1) per-plugin `mobile.yaml` (`modules[]` with `screen: registry|spec`, `screen_token`, `surfaces`, `cards[]` pointing at `widgets.yaml`); (2) bootstrap merge — build `modules/quick_actions/more_actions/drawer_sections` from installed plugins' `mobile.yaml` **plus** a `widgets` array filtered to `surfaces: [mobile]`, replacing the ~300 lines of hardcoded rules behind a golden test pinning current output per role; (3) client `SpecWidget` (`Map<String, SpecRenderer>` over `stat_card.dart`/`paginated_list.dart`/etc.) and per-app `MOBILE_SCREEN_REGISTRY` with unknown-token fallback to `module_screen_template.dart`; (4) `plugin_provider.dart` parses+caches the new fields offline. Net rule stands: a new mobile **card** = YAML only; a new mobile **screen** = registry token + app release, now explicit.

## 12. ONE-LINE VERDICTS
- **v2-shipped**: engine complete and tested (adapter, aliases, validator+CI, doctor, config v2+secrets+migrations, widget contract backend+frontend, 23 widgets) — but adopted by zero manifests.
- **v1-residue**: 41/41 module manifests v1-shaped; ratchet coded (`validator.py:229-231`) yet never fired; legacy dir + hardcoded fallback maps still live.
- **unused-contract-fields**: ~25 v2 manifest keys + events.yaml/mobile.yaml/permissions.yaml sidecars unused; `config_migrations.py` count is 0 and its load-time validator rule is missing.
- **events**: runtime bus real (19 handlers, startup-wired), declared contract absent; plugins cannot ship listeners.
- **widgets**: contract + gating + one component widget solid; a school cannot reorder, configure, hide, or persist any widget (no layouts table, no config merge, no UI).
- **theme+parity**: v1 duplicated registries only; no resolver/tokens; parity lock not built — nothing broken only because nothing touched themes yet.
- **website dynamism**: W-01 done, W-03 done (minus hreflang), W-04 backend done (no UI, no profile fields), W-2 partial; single-fetch SSR seam ready for `plugin_sections`.
- **template packs**: none exist; `tools_gen_*` feed only the designer folder scanner; plugins have no website channel; §9 spec is the minimal additive path.
- **mobile**: `flutter:`/`mobile:` manifest keys consumed by nothing; bootstrap is hardcoded rules; path specced in §10.
