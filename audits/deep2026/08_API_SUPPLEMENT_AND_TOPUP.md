# API-layer supplement + agent-relaunch outcome (2026-09-03)

The six terminated agents could not be relaunched: every retry (including staggered ones) failed with `user concurrency limit exceeded` — the account-level agent quota was saturated. This file covers what those agents would have delivered, produced by main-session inspection instead: a targeted API-layer audit plus the decision-relevant research top-ups.

## 1. Backend API audit — new findings (main session)

Prior audits (backend core, AI, datamodel, plugins, website) already covered auth/users/schools/superadmin/plugins/website/design_studio/webhooks/payments. This pass targeted fees/exams/hr/parent/student/communications/library/attendance/transport.

**A-1 (P1) Marks entry accepts marks above full marks.** `exams.py:630-788 submit_marks`: the pre-validation loop (E17-class guards — genuinely good: batch-fails on bad ids/tenant mismatches before any write, single transaction) checks student/subject/class existence and teacher scope, but **never checks `theory + practical <= full_marks`**. The write loop (`:720-725`) converts to float and stores; grade is computed from the inflated total → a teacher can enter 150/100 and it grades A+. No clamp, no 400.
Fix: in the pre-validation loop, resolve full marks (same `_first_float` chain used at `:67-108`) and reject `theory > theory_full` / `practical > practical_full` with `records[idx]` context. Acceptance: test posts 150/100 → 400 naming the row.

**A-2 (P1) Concurrent marks submissions create duplicate rows.** `:733-737` does check-then-insert on `(school, exam, student, subject)` with no unique constraint (datamodel P0-3) and no lock. Two teachers/clients submitting the same student+subject simultaneously → both `existing is None` → two Marks rows; every aggregate doubles.
Fix: D-02's unique constraint + `ON CONFLICT DO UPDATE` upsert (or `with_for_update` on the candidate rows).

**A-3 (P1) Broadcast recipients are silently capped at 500.** `communications.py:339` `_users_for_audience(audience, class_id, limit=500)`. A school with 800 parents sends an "all_parents" broadcast; 300 get nothing — no warning, no pagination, no error. Same helper backs push fan-out.
Fix: paginate the audience, or make the limit explicit + warn in the response meta (`recipients_capped: true`).

**A-4 (P1) Library checkout is a check-then-act race.** `library.py:175` checks `available_copies <= 0`, `:211` decrements — no row lock, no constraint. Two concurrent checkouts of the last copy → negative stock. Same class for returns (`:237`). Only 2 `with_for_update` uses exist in the entire API (student-number issuance `iemis_importer.py:541`, student create `students.py:150` — both good); every other counter is unlocked.
Fix: `SELECT … FOR UPDATE` on the Book row inside the transaction (or `UPDATE books SET available_copies = available_copies - 1 WHERE … AND available_copies > 0` returning rowcount).

**A-5 (P2) Exam rank has no tie handling.** `exams.py:972-975` and `:1123-1126` sort by percentage and assign sequential ranks — two students with equal percentage get different ranks (standard competition ranking 1,1,3 is what Nepali schools expect on report cards).
Fix: assign `rank = 1 + count(rows with strictly greater percentage)` (or dense rank, configurable).

**A-6 (P2) Payroll tax is a single flat rate on basic.** `hr_payroll.py:225-287`: `taxRate` from plugin config, applied as `basic * tax_rate / 100`. No slabs, no SSF/PF split, not computed on gross. Documented simplification, not a calculation bug — but Nepal payroll (SSF 31%/20% splits, annual SST slabs) will require the structure in the plan's C-10/N-07 work. Also `deductions["Tax"]` string-keyed in JSONB (normalization already planned).

**A-7 (verified-good) items this pass confirmed:** attendance percentage `(P+L)/T` consistent across endpoints (`attendance.py:248,354,393`); VAT extraction is inclusive-correct (`fees.py:2754-2756` `base = amount / (1 + vat/100)`); timetable conflict detection in `timetable.py:176-224` is real (class + teacher + time-window overlap → 409); parent_app correctly scopes every child query through the Guardian join + `_pick_students` (`parent_app.py:57-87`) — no cross-child leak found; promotion logic has status guards and roll-strategy handling (`students.py:392-493`).

**A-8 (P2) Everything else in the mobile/parent/student surface confirmed the earlier findings** — mobile routes mostly ungated (already planned as P-05.7), no new classes of defect found beyond those.

## 2. Research top-ups (main-session web research)

### Nepal curriculum / spec grids (feeds plan A-03/A-04)
- CDC Sanothimi publishes per-subject "परीक्षा विशिष्टीकरण तालिका" (specification grids) as annexes to the 2076+ curriculum: per-unit rows with question counts by type (अति छोटो/छोटो/लामो — very short/short/long) and cognitive level (ज्ञान/सीप/अनुप्रयोग/उच्च सीप — knowledge/understanding/application/higher ability), totaling the subject's full marks. The canonical Grade 10 pattern: Group A अति छोटो (1×n), Group B छोटो (short, 2-5 marks), Group C लामो (long, 4-10 marks) with internal choice ("वा") inside groups; 75% theory / 25% internal assessment at secondary (50/50 for CS and some vocational subjects).
- Official sources: moest.gov.np, cdc.gov.np (curriculum + curriculum-grade 9-10 spec grid PDFs), see.gov.np (SEE exam specs), neb.gov.np (Grade 12). SEE 2082 internal-assessment notice enumerates 139 subject codes with THFM/THPM/PRFM/PRPM.
- **Implementation note for A-03/A-04:** model the spec grid as `CurriculumUnit` rows carrying `{question_type, count, marks_each, bloom_level}` tuples (exactly the `BlueprintCell` shape already specified in the plan) with a "CDC default grid" per grade+subject that a school can copy and edit. Question-paper wording should support bilingual prompts: Nepali instructions (`समूह 'क' : अति छोटो उत्तरात्मक प्रश्नहरू`) with English subject matter, matching real papers.
- BS calendar authority: variable month lengths are published by Patro apps/astro agencies; the codebase's two sources (frontend `BS_DATA` table 2000-2089, backend `nepali-datetime` package) are both fine — plan item N-06 (single source) stands.

### AI engineering (feeds A-01/A-05/A-06)
- **Structured outputs (2026):** OpenAI `response_format: json_schema` (strict mode, supported schemas subset), Anthropic forced tool-use (single tool with input_schema) and newer structured-output support, Gemini `responseSchema`. For Groq (the platform's primary), JSON mode exists but full schema-constraint support is limited → the plan's `parse_and_validate(schema, text)` + one bounded repair retry is the right cross-provider pattern; use Pydantic for schemas and log `repair_attempts` in usage metadata.
- **Embeddings for Nepali:** `intfloat/multilingual-e5-large` and `BAAI/bge-m3` are the strongest open multilingual choices (bge-m3 handles 100+ languages, 8192 ctx, dense+sparse+colbert in one model — ideal for hybrid search in Postgres); OpenAI `text-embedding-3-small/large` as the managed path. Dimension note: the dead `students.embedding` is 1536 (OpenAI dims); bge-m3 is 1024 — the plan's `document_chunks(embedding vector(1024))` matches bge-m3.
- **Prompt caching:** Anthropic cache_control gives up to 90% discount on cached prefix tokens; OpenAI automatic caching ~50% on cached input; batch APIs ~50% for async jobs (report-card remark batches are the ideal batch use case — no user waiting).
- **Observability:** Langfuse (self-hostable, MIT) fits the existing Postgres/Redis stack better than LangSmith (SaaS-only) — log prompts, completions, latencies, costs per feature/school; OpenTelemetry GenAI semconv for traces.
- **OCR for handwritten Devanagari (for A-06 handwriting grading):** cloud — Google Document AI / Azure Document Intelligence have the best Indic-script handwriting support; open — Surya OCR (good Devanagari) + TrOCR. Handwritten-math grading accuracy is still unreliable everywhere (Gradescope does AI-assisted *grouping*, not full auto-grading). Confirms the plan's stance: reject photo-only submissions now; vision ingestion later as assisted-transcription with confidence flags and teacher review, never as verdict.
